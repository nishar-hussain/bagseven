# x402 v2 on Polygon Amoy

Bagseven now parses the official x402 v2 `PAYMENT-REQUIRED` format and validates
the selected `exact` option against the active BagMandate policy:

- network must be `eip155:80002`;
- asset must be the configured Polygon Amoy USDC contract;
- `payTo` must be a valid EVM address;
- amount is an integer USDC atomic-unit string;
- per-purchase, window, lifetime, and vault limits are checked before signing.

## Why settlement is currently fail-closed

The current `BagMandate` contract owns the USDC and exposes `execute(amount,
recipient, workerId)` to its enforcer. It does not implement
`transferWithAuthorization` and it cannot produce an EIP-3009 EIP-712 signature.
The x402 `exact` EVM scheme requires a payer signature over
`transferWithAuthorization`; the official SDK therefore needs a signer whose
USDC balance is the payer. Using the operator key or a separate daemon EOA
would move funds outside the vault and bypass the mandate.

For that reason, x402 v2 requests currently return
`X402_VAULT_EIP3009_UNSUPPORTED` after challenge and policy validation. No
reservation, signature, transaction, or provider retry is performed.

## Safe implementation options

1. Add a vault-compatible x402 settlement contract/facilitator path. The
   settlement contract must atomically check the worker, caps, recipient,
   amount, nonce, and vault balance, then settle the provider payment while
   remaining the final authority. The provider must accept that settlement
   path rather than requiring EIP-3009 from the vault address.

2. Use a dedicated payer account with its own USDC and an explicit, auditable
   linkage to a BagMandate reservation. This is only safe if the mandate
   authorizes the payer account and the settlement/reconciliation path prevents
   spending outside the reservation. It must not reuse the operator key by
   convention.

The existing Bagseven provider challenge flow remains unchanged.
