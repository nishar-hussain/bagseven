# x402 v2 on Polygon Amoy and Avalanche Fuji

Bagseven now parses the official x402 v2 `PAYMENT-REQUIRED` format and validates
the selected `exact` option against the active BagMandate policy. The active
process may target Polygon Amoy or Avalanche Fuji:

- network must match the configured chain (`eip155:80002` or `eip155:43113`);
- asset must be the configured USDC contract for that chain;
- `payTo` must be a valid EVM address;
- amount is an integer USDC atomic-unit string;
- per-purchase, window, lifetime, and vault limits are checked before signing.

## Isolated testnet payer

For controlled testnet testing, Bagseven supports an opt-in isolated payer
EOA configured with `BAGSEVEN_X402_PAYER_KEY`. It is deliberately different
from the worker operator and contract enforcer. The flow is:

1. validate the provider challenge and mandate limits;
2. reserve the request and fund the isolated payer through `BagMandate.execute`;
3. sign the x402 EIP-3009 authorization with the isolated payer key;
4. retry the provider with `PAYMENT-SIGNATURE`;
5. release the reservation and refund the payer if the provider rejects payment.

By default, the payer must have a zero USDC balance before each request. This
prevents previous funds from being reused for an untracked purchase. For a
controlled testnet wallet, `BAGSEVEN_X402_PAYER_ALLOW_NONZERO=true` permits an
existing balance, but then Bagseven cannot prove that the provider payment used
only the current mandate-funded amount. The key must never be the operator or
enforcer key, and it must be stored in a secret manager in production.

The existing BagMandate contract remains the budget authority. The payer is
only a temporary EIP-3009 compatibility bridge for providers that do not accept
Bagseven-native settlement. This is restricted to the configured Polygon Amoy or
Avalanche Fuji testnet and must not be used with mainnet funds.

## Safe implementation options

1. Add a vault-compatible x402 settlement contract/facilitator path. The
   settlement contract must atomically check the worker, caps, recipient,
   amount, nonce, and vault balance, then settle the provider payment while
   remaining the final authority. The provider must accept that settlement
   path rather than requiring EIP-3009 from the vault address. This is the
   preferred production architecture.

2. Use a dedicated payer account with its own USDC and an explicit, auditable
   linkage to a BagMandate reservation. This is only safe if the mandate
   authorizes the payer account and the settlement/reconciliation path prevents
   spending outside the reservation. It must not reuse the operator key by
   convention.

The existing Bagseven provider challenge flow remains unchanged.
